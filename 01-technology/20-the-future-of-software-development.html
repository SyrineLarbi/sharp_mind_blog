The Future of Software Development. Writing code was never the hard part. Deciding what to build, and making sure it works, still is.

Since 2022, AI tools have learned to write working code from a sentence of plain English. That has led to two confident predictions: that programmers will soon be obsolete, and that nothing important will change. History suggests both are wrong. Every earlier leap in programming tools, from the first compilers to the cloud, made developers far more productive, and the world responded by wanting far more software. To judge what happens next, you need to know what developers actually spend their time on, and which parts of that work AI really does well.

Question 1 · What is it?

Turning a vague human wish into exact instructions

Software development is the work of designing, writing, testing, running and maintaining computer programs. Writing the code itself is only one part, and often not the largest one.

Chapter 01

The software crisis of 1968

In 1968 NATO organised a conference in Garmisch, Germany, on a problem that worried governments and companies alike. Large software projects were running years late, far over budget, and often did not work when delivered. Participants called it a "software crisis". The conference helped popularise the term software engineering: the idea that building programs should be a disciplined engineering practice rather than clever improvisation. Margaret Hamilton, who led the team writing the onboard flight software for NASA's Apollo missions, is often credited with using the term in the same period to argue that software deserved the same respect as hardware.

Seven years later Fred Brooks, who had managed a huge IBM software project, published The Mythical Man-Month. Its most famous lesson became known as Brooks's law: "adding manpower to a late software project makes it later." New people need training, and every extra person adds more conversations to coordinate. The book's deeper point was that software is hard not because typing code is slow, but because understanding and coordinating a complex system is slow. That point is the key to everything that follows.

Chapter 02

What developers actually spend their time on

Outsiders picture a programmer typing code all day. In practice, writing new code is only part of the job. Studies and surveys of developers consistently find that much of their time goes on other activities.

ActivityWhat it involves
Understanding the problemTalking to users and colleagues, working out what is really needed, writing down requirements
Reading existing codeMost work changes software that already exists, often millions of lines written by others years ago
DesigningDeciding how the parts fit together, how data flows, what can fail
Writing codeThe part most people imagine
Testing and debuggingChecking it works, finding out why it doesn't, fixing it
ReviewingReading colleagues' changes before they are accepted
Running and maintainingKeeping it working, secure and up to date for years

This matters for the future. A tool that makes typing code ten times faster does not make the whole job ten times faster, because typing was never most of the job. The real question is how much AI helps with the other rows.

Chapter 03

The ladder of abstraction

The history of programming is a ladder. Each step lets people say more with less, by hiding detail underneath. In the 1940s programmers wrote raw machine code, the numbers a processor executes directly. Then came assembly language, short names for those numbers. In the 1950s Grace Hopper built early compilers, programs that translate human-readable instructions into machine code, and helped create the business language COBOL. John Backus's team at IBM released FORTRAN in 1957.

Each step up brought the same fear and the same result. Experienced programmers doubted that compiled code could ever be as good as hand-written assembly. Within years, almost nobody wrote assembly by hand. Later steps added ready-made libraries of code, shared freely as open source, and then the cloud, where a few lines can rent a thousand servers. AI that writes code from plain language is the newest step on the same ladder, and possibly the largest. The question is whether it is a step like the others, or a different kind of thing.

Question 2 · How does it work?

How modern software is built, and where AI fits in

Today's software is built by teams, from shared parts, through an automated pipeline. AI tools are being fitted into every stage of that pipeline.

Chapter 04

The modern pipeline

Most software teams today work in short cycles, an approach summed up in the Agile Manifesto written by a group of developers in 2001. Instead of planning everything for a year and delivering at the end, they build a small piece, show it to users, and adjust. Code is kept in a version control system, usually Git, created by Linus Torvalds in 2005, which records every change and lets many people work on the same code without overwriting each other.

The automated middle part is called continuous integration and continuous delivery (CI/CD). Its value is that mistakes are caught minutes after they are made, not months later. A habit closely linked to it, called DevOps, gives the same team responsibility for building software and for running it, so developers feel the consequences of fragile code.

Chapter 05

Built from other people's code

A typical modern application contains far more code written by strangers than by its own team. Developers assemble programs from open-source packages: free, shared components for everything from reading dates to encrypting passwords. One package depends on others, which depend on others again. These are called dependencies.

This is enormously efficient and also fragile. In December 2021 a flaw called Log4Shell was found in Log4j, a widely used open-source tool for recording what a program is doing. It affected a huge number of systems worldwide, many of whose owners did not know they used it. In 2024 a developer named Andres Freund noticed a tiny slowdown on his computer and traced it to a hidden backdoor in xz, a small compression tool included in many Linux systems. Someone had spent years gaining the trust of the project's volunteer maintainer in order to insert it. Much of the world's software rests on small projects kept alive by a few unpaid people.

Chapter 06

AI coding assistants: from autocomplete to agents

The large language models described in Volume 49 are trained on huge amounts of text, including public code. Code turns out to suit them well: it is highly structured, there is a great deal of it online, and it can be checked automatically by running it. Three generations of tools appeared quickly.

Autocomplete

GitHub Copilot, previewed in 2021, suggests the next lines of code as you type, like predictive text for programmers. The developer stays fully in control, accepting or rejecting each suggestion.

Chat

From late 2022, chat assistants could write a whole function, explain unfamiliar code, or suggest why a program crashed, from a plain-language request.

Agents

From 2024, coding agents could take a task, read a codebase, make changes across many files, run the tests and try again when they failed. Examples include Cursor, Claude Code and GitHub's own agent features.

In early 2025 the AI researcher Andrej Karpathy coined the term "vibe coding" for building software by describing what you want and accepting what the AI produces, without reading the code closely. It is fun and fast for small personal projects. For software that handles money, health or private data, it is a risky way to work, because nobody understands what was built.

Chapter 07

Why the tests matter more than ever

An AI model generates code that looks right, based on patterns. Like the text models in Volume 49, it can be confidently wrong. It may call a function that does not exist, mishandle an unusual case, or introduce a security hole. The best defence is something software engineering already had: automated tests, small programs that check whether other programs behave correctly.

This is why AI is especially strong where answers can be checked. If a test suite says clearly whether a change works, an agent can try, fail, read the error and try again, many times, quickly. Where "correct" is vague, such as "make this easier to use" or "design this so it can grow for ten years", the human still has to judge. The more precisely you can say what "working" means, the more of the work a machine can do.

Question 3 · Why does it matter?

Software runs everything, so how it is built affects everyone

Banks, hospitals, aircraft, power grids and phones all run on software. Changes in how it is made affect cost, safety and jobs far beyond the technology industry.

Chapter 08

What the evidence says about productivity

The evidence so far is mixed, and the details matter. In a controlled experiment published by GitHub researchers in 2023, developers using Copilot finished a well-defined programming task about 55 per cent faster than those without it. In October 2024 Google's chief executive said that more than a quarter of all new code at the company was being generated by AI and then reviewed by engineers.

Other evidence points the other way. In 2025 the research group METR ran a randomised study with experienced open-source developers working on large projects they knew well. With AI tools they took about 19 per cent longer, even though they believed the tools had made them faster. The likely reasons included time spent prompting, waiting and checking output that was not quite right.

These results are not contradictory. AI helps most on small, well-defined, unfamiliar tasks, and least on large, complex systems that an expert already knows deeply. Studies of this kind are also overtaken quickly, because the tools improve every few months. The honest summary for 2025 is a large gain on some work, little or none on other work, and a real risk of overestimating your own speed-up.

Chapter 09

When software fails

Software failures can be spectacular. In 1996 the first flight of the European Ariane 5 rocket ended in an explosion about 40 seconds after launch. Code reused from the earlier Ariane 4 tried to squeeze a number too large for its storage space, and the guidance system shut down. In July 2024 a faulty update from the security company CrowdStrike crashed about 8.5 million Windows computers worldwide, grounding flights and disrupting hospitals and banks for days.

Neither failure was caused by AI. They are reminders that the cost of software errors grows with how much of the world depends on software. If AI greatly increases the amount of code written, the amount of code that must be understood, tested and maintained grows too. Research has found that AI assistants can suggest insecure code, especially when asked to do security-sensitive tasks. Faster writing without stronger checking would simply produce more failures, faster.

Chapter 10

Jobs: fewer programmers, or more software?

The economic argument divides into two camps. The first says that if AI does much of the coding, companies will need fewer developers. Entry-level roles, where juniors traditionally did simpler coding tasks, are the most exposed, and from around 2023 many reports described a tougher market for new graduates in software. How much of that was caused by AI, rather than by higher interest rates and cuts after a hiring boom, is disputed.

The second camp points to history. When something becomes cheaper, people often want much more of it. Economists call this the Jevons paradox, after a 19th-century observation that more efficient steam engines increased total coal use. Compilers, open source and the cloud each made software far cheaper to build, and the number of developers grew. Huge amounts of useful software are never built today because they are too expensive: tools for small businesses, local governments, charities, and individuals.

Both effects can happen at once. The likeliest outcome is a changed job rather than a vanished one: less time typing routine code, more time on deciding what to build, designing systems, reviewing machine output and taking responsibility for it. The open worry is how juniors will learn the craft if the simple tasks that used to train them are automated. The broader picture is in How work may change because of AI.

Question 4 · Advantages and disadvantages

Faster building, and the cost of not understanding

AI coding tools bring real gains. Each gain has a matching risk, usually about understanding and responsibility.

Chapter 12

The comprehension debt

Developers already use the phrase technical debt for shortcuts that save time now and cost more later, like borrowing money. Code written quickly without good structure has to be "repaid" with painful rework. AI adds a related risk that some engineers call comprehension debt: code that works today but that nobody on the team actually understands.

The danger shows up later. When that code breaks at three in the morning, or must be changed for a new law, someone has to understand it. If nobody does, the team is at the mercy of the next AI suggestion. Responsibility cannot be delegated to a tool. When software fails, the company and its engineers answer for it, not the model. Good teams therefore treat AI output like a fast but inexperienced colleague's work: useful, often impressive, and always reviewed.

Chapter 14

Safer languages, proofs, and the skills that last

Two quieter trends may matter as much as AI. The first is a move to memory-safe languages. Microsoft and Google have each reported that roughly 70 per cent of their serious security bugs came from memory-safety errors, mistakes that older languages like C and C++ allow and newer ones like Rust prevent by design. In 2024 the US government publicly urged software makers to move towards memory-safe languages. The second is formal verification: proving mathematically that a program does what its specification says. It is slow and expensive, but it has been done for real systems, such as the seL4 operating system kernel. AI may make it far cheaper, because a machine-checked proof is exactly the kind of answer that can be verified automatically.

Put together, these trends point in one direction. As writing code becomes cheap, the valuable skills become knowing what to build, describing it precisely, and proving that it works. Those were always the hard parts that Fred Brooks wrote about in 1975. The developers who thrive will be those who understand systems deeply enough to direct machines and to catch them when they are wrong. That is a different job from typing code, but it is still engineering.

The core idea

Software development is much more than writing code: understanding needs, designing, testing and maintaining take most of the effort. AI tools are the newest step on a long ladder of abstraction. They help most where correctness can be checked, and least where judgement and deep system knowledge are needed. Responsibility stays with humans.

The numbers worth knowing
  • 1968: the NATO conference on the "software crisis".
  • 2023: about 55 per cent faster on a defined task with Copilot (GitHub study). 2025: about 19 per cent slower for experts on their own large projects (METR).
  • Roughly 70 per cent of serious security bugs at Microsoft and Google came from memory-safety errors.
The common mistake

Thinking that if AI writes code ten times faster, software gets built ten times faster. Typing was never the bottleneck. Understanding and checking were.

Test yourself

Can you explain why an AI agent does better on a task with good automated tests than on one with vague goals? If you can, you understand where AI helps in software and where it does not.
